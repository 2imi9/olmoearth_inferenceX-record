## Context

The repository holds two things that are usually kept apart: a small Python package that people can install, and the research record that justifies it.

- `oe_inferencex/` is 16 flat modules, about 2,800 lines, with a public surface of 55 names declared in `__init__` (release 1.0.0). By dependency the modules fall into three groups: eight need only numpy (`metrics`, `signals`, `stats`, `assess`, `explain`, `compare`, `calibrate`, `reliability`), two need only the standard library (`taskcard`, `lcc`), and four import something heavy behind a guard that names the extra to install (`evidence` needs torch; `awf` and `data` need the encoder and geo extras; `figstyle` needs matplotlib). `cli` sits on the numpy group. The [Usage page](https://olmoearth-inferencex.readthedocs.io/en/latest/Usage/) already tabulates the modules along these lines.
- [`exp/`](../../exp/) is the record: 75 numbered scripts, four helpers, and the [lab log](../../exp/NOTES.md). 70 of the 79 scripts import the package by module path, as do 11 of the 12 test files. `exp/out/` holds 203 tracked artifacts, about 250 MB in total, the largest 66 MB.
- The [claim ledger](../method/claims.md) (`docs/claims.yaml`, 143 claims) pins every documented number to a path under `exp/out/`; `tests/test_claims.py` and `scripts/claims.py stale` read those paths from the working tree.
- The numbers for exp64, exp72, exp73 and exp74 came from 17 job scripts that exist only in the home directory on the aicr cluster (100 GiB, seven-day snapshots; scratch is purged after 30 days). The repository has never seen them.
- The API reference is generated by walking the package tree (`docs/gen_api.py`), so subpackages would be picked up there without changes.
- Decisions already taken: no CI/CD (2026-09-16); finishing means a licence, a citation file and a tagged release; the workload stays light.

The counts above are as of the decision. Later the same day the ledger reached 146 claims, exp74's 362 files joined `exp/out/`, and an audit of every tracked file ([cleanup audit](cleanup-audit-2026-09-17.md)) removed 28 outdated files, mostly figure sources and build products nothing used, and then, at the author's choice, 414 more (item 6).

The forces: the record must stay reproducible from one tag; people who only want the package must find it quickly; nothing should move under the ledger's pins; and the layout should not need revisiting at every new experiment.

## Decision

Option A below: keep the package flat, keep the record where it is, add `exp/jobs/` for the cluster scripts, and clean the root. In outline:

```
olmoearth_inferenceX/
  oe_inferencex/        the package, flat; three dependency groups documented, not split
  tests/                one file per module, plus the package, claims and recorded-value tests
  examples/             quickstart.py
  scripts/              claims.py, audit_one_scene.py
  exp/                  numbered scripts, helpers, NOTES.md; out/ is what the ledger pins
    jobs/               NEW: the sbatch, serve and container scripts, verbatim, with a README
  docs/                 the mkdocs site; claims.yaml lives here
  report/               the technical report: main.tex, references.bib, main.pdf
  README.md  CHANGELOG.md  CITATION.cff  pyproject.toml  LICENSE (once chosen)
```

## Options considered

### Option A: flat package, record in place, add `exp/jobs/`

| Dimension | Assessment |
|---|---|
| Complexity | Low: no code moves; one new folder and a gitignore line |
| Cost | Half a day: fetch 17 scripts through one cluster job, write their index, clean the root |
| Scalability | Fine to roughly 25 modules and a few hundred artifacts; revisit triggers below |
| Team familiarity | Highest: nothing changes for anyone who has read the code or the docs |
| Record integrity | Improved: the job scripts join the tag whose numbers they produced |

**Pros:** every recorded number stays reproducible from one commit; the Usage page's module table already explains the grouping; the one missing reproducibility piece gets added.

**Cons:** the package looks flat to readers used to library trees; `exp/` stays long and leans on the lab log as its index.

### Option B: subpackages by dependency (`core`, `adapters`, `extras`)

| Dimension | Assessment |
|---|---|
| Complexity | Medium: three subpackages, re-exports to keep the 1.0 surface identical |
| Cost | A day, then ongoing: imports in 70 experiment scripts and 11 test files, doc paths, the ledger's citation file lists if docs pages move |
| Scalability | Good once the package passes a few dozen modules; no gain before that |
| Team familiarity | Medium: the same functions under longer paths |
| Record integrity | Neutral only if the re-exports are exact; proving it means re-running the experiments or keeping a compatibility shim |

**Pros:** the dependency boundary becomes visible in the tree, not just in the guard messages.

**Cons:** the change is cosmetic at 2,800 lines; it touches 81 files that are part of the record; the declared surface has to be kept identical by hand.

### Option C: two repositories, library and record

| Dimension | Assessment |
|---|---|
| Complexity | High: cross-pinning, two release cadences, two docs sites or one that reads both |
| Cost | Days, then a permanent tax on every recorded run |
| Scalability | Best for a library many projects depend on; not the situation today |
| Team familiarity | Low: the record's scripts would import a pinned wheel, not the tree they were written against |
| Record integrity | Weakened: reproducing a number means matching two commits, and the ledger's path pins would cross a repository boundary |

**Pros:** a clean install target; the record could grow without enlarging the package repository.

**Cons:** the single-tag guarantee is the project's main reproducibility property and this breaks it. It becomes the right move only if the library is adopted elsewhere, and it can then be extracted at a tag.

### Option D: artifacts out of git (LFS, a Hub dataset, or release assets)

| Dimension | Assessment |
|---|---|
| Complexity | Medium: a download step before the ledger tests can run |
| Cost | Low to set up; LFS bandwidth or Hub hosting to keep |
| Scalability | Needed if `exp/out/` approaches 1 GB or any file passes 100 MB |
| Team familiarity | Medium |
| Record integrity | Weakened: the tests that check the numbers would depend on a fetch, and the tag would no longer contain what it certifies |

**Pros:** small clones.

**Cons:** at 250 MB the problem does not exist yet, and the largest file (66 MB) is under GitHub's hard limit.

## Trade-off analysis

The decisive force is that any recorded number can be reproduced from one tag of one repository, and that the tests which check the ledger read the artifacts from the tree they run in. Options B, C and D each spend something against that: B spends churn on 81 record files for a boundary the import guards already enforce; C splits the tag; D splits the artifacts from their checks. Option A spends nothing and fixes the one real gap, the unversioned cluster scripts. The cosmetic argument for B is real but small at this size, and the API reference already renders one page per module, which is where a reader looks for structure.

## Consequences

- Easier: reproducing any recorded run, including the served-model and multi-encoder jobs, from the tag; onboarding through the Usage page's module table; submitting a cluster job from the repository instead of from a home directory.
- Harder: nothing new; the long `exp/` folder remains, indexed by the lab log.
- Revisit when: the package passes about 25 modules or gains a second heavy dependency family (then B); the tracked artifacts near 1 GB or any file nears 100 MB (then D); Ai2 adopts the code into rslearn or the agent (then C, extracted at a tag).
